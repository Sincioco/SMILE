# 008 - SMILE - INPUT Statement Official Specification v1.0

## Status

This is the current official specification for the SMILE `INPUT` statement.

This revision implements the beginner-first Strategic Reset. It supersedes the earlier v1.0 requirements for a shared strict UTF-8 byte algorithm, a universal 4096-byte line limit, embedded-NUL console-input preservation, identical line-ending edge behavior, identical runtime-error text, and byte-for-byte all-target runtime parity.

The permanent project principles and authority order are defined by:

- `AGENTS.md`;
- `docs/SMILE Core Principles.md`.

Companion language behavior remains defined by the current official LET, SET, PRINT, String, core-expression, IF, comment/layout, and WHILE specifications in this directory.

## 1. Purpose

`INPUT` reads one line from standard input and assigns the entered value to an already-declared variable according to that variable's fixed SMILE type.

```smile
LET Name = ""

PRINT Enter your name:
INPUT Name

PRINT Hello {Name}!
```

`LET` declares the variable and establishes its type. `INPUT` changes its current value at runtime without changing that type.

## 2. Canonical Syntax

The only official syntax is:

```text
INPUT variable
```

`INPUT` is case-insensitive. The target is resolved with SMILE's ordinal case-insensitive identifier lookup.

```smile
INPUT Name
input Age
Input Continue
```

Formal grammar:

```text
input-statement -> INPUT hspace+ identifier hspace* statement-end
hspace          -> space | tab
statement-end   -> line-end | end-of-file
```

The statement accepts exactly one existing identifier.

## 3. Curly Braces Are Not Variable Delimiters

Curly braces `{ }` identify interpolation holes in text-oriented syntax. They are not general variable-reference delimiters.

The variable is therefore written directly:

```smile
INPUT Name
```

This is invalid:

```smile
INPUT {Name}
```

The following are also invalid:

```smile
INPUT
INPUT Name, Age
INPUT "Prompt", Name
INPUT Name AS String
INPUT GetName()
```

## 4. INPUT Is A Statement

`INPUT` is a statement, not an expression. It cannot appear in a LET or SET expression, interpolation hole, IF condition, or WHILE condition.

Invalid:

```smile
LET Age = INPUT
PRINT {INPUT Name}

IF INPUT Age >= 18 THEN
END IF
```

INPUT performs no hidden call while an IF or WHILE condition is evaluated.

## 5. Existing Variable And Fixed Type

The target must have an earlier successful `LET` declaration.

```smile
LET Age = 0
INPUT Age
```

An undeclared target is invalid:

```smile
INPUT Age
```

The existing type determines the ordinary conversion:

| Existing SMILE type | INPUT meaning |
|---|---|
| `String` | Read one normal line of text as the new String value |
| `Integer` | Convert ordinary signed decimal Integer text using a normal native target facility |
| `Boolean` | Convert the approved `TRUE` or `FALSE` representation, ordinal case-insensitively |

`INPUT` never declares a variable and never changes the type established by `LET`.

## 6. Relationship Among LET, SET, And INPUT

```text
LET    declares a variable and establishes its initial value and type
SET    changes an existing variable from a SMILE expression
INPUT  changes an existing variable from one runtime input line
```

`SET` and successful `INPUT` update the same current runtime storage. Later statements read the newest value.

## 7. Where INPUT Is Permitted

`INPUT` is permitted:

- at top level;
- in IF, ELSE IF, and ELSE bodies;
- in nested IF bodies;
- in WHILE bodies, including nested control flow.

Only a reached `INPUT` consumes input. An unselected branch or zero-iteration loop body consumes nothing.

LET remains prohibited in IF and WHILE bodies under their current separate specifications.

## 8. Beginner-First Native Input Rule

Generated targets must use the ordinary native construct a beginner would reasonably learn for the destination language whenever practical.

For the current active targets, the intended direction is:

| Target | Normal direction |
|---|---|
| C# | `Console.ReadLine()` with conventional String, Integer, or Boolean conversion |
| C | `scanf` for simple numeric input and `fgets` when line-oriented String input is needed |
| Windows x64 MASM | Straightforward CRT/Win64 calls such as `scanf`, with clear variable storage |

Do not replace a simple native operation with a generated byte reader, UTF-8 validator, parser state machine, common byte-limit subsystem, generic error dispatcher, or target-neutral runtime API merely to reproduce obscure edge cases identically across unrelated runtimes.

A helper is permitted only when an approved current SMILE rule genuinely needs it and the helper is the smallest clearer solution.

## 9. Conceptual Input Behavior

Each executed INPUT requests one ordinary logical line from the destination's standard-input facility.

For normal valid interactive or redirected input:

- String input reads the line's text without interpreting SMILE source escapes;
- Integer input accepts ordinary signed decimal text supported by the selected conventional conversion;
- Boolean input accepts `TRUE` or `FALSE` without case sensitivity;
- the converted value becomes the target variable's current value;
- later PRINT, LET, SET, IF, and WHILE operations read that current value.

The line terminator itself is not part of the ordinary String value.

## 10. Target-Native Edge Behavior

The following are deliberately **not** universal SMILE runtime requirements:

- a byte-for-byte redirected-input algorithm;
- strict UTF-8 validation implemented identically by every target;
- a shared 4096-byte maximum;
- embedded-NUL preservation in line-oriented console input;
- identical CRLF, LF, standalone-CR, and final-EOF edge handling;
- identical locale-independent parser internals;
- identical exception types, stderr wording, or host-library diagnostics;
- identical behavior for malformed byte streams or other obscure host/runtime edges.

Targets should use their normal facilities and document a meaningful target-specific limitation when one matters. Do not simulate a richer cross-language runtime merely to erase an obscure native difference.

This native-edge rule does not permit stale-value propagation, skipped INPUT statements, hidden input operations, or changing the variable's SMILE type.

## 11. Conversion Failure

Invalid or unavailable input is a runtime failure, not a compile diagnostic.

The reference evaluator must contain the failure and return a sensible `SmileRuntimeError` rather than crash its host. It must preserve output already produced, stop later SMILE statements, provide a concise diagnostic, and report unsuccessful completion.

Generated targets may use the normal destination-language failure mechanism or a small clear check. They are not required to reproduce the evaluator's exact error code, message text, byte boundary, or exit status for obscure invalid-input cases.

No automatic retry is hidden inside `INPUT`. A future explicit language feature may define retry or structured error handling.

The earlier `SMILER1502` 4096-byte-limit behavior is superseded and is not part of the current INPUT contract. Other existing evaluator input-error identities may remain useful as evaluator diagnostics, but they do not impose a generated cross-target error-dispatch runtime.

## 12. Successful Assignment

On successful conversion, INPUT assigns the new value as one runtime update. A conversion that fails must not be treated as a successful new value.

An implementation may naturally combine declaration and first input operation in generated code when ordinary program behavior is preserved and the result is clearer. This is target lowering, not a hidden change to SMILE's declaration-before-input rule.

## 13. Runtime-Unknown Analysis

After INPUT:

- the target variable's type remains known;
- its value is runtime-unknown;
- its earlier LET or SET value must not be propagated past the INPUT;
- branch and loop analysis must merge paths conservatively;
- later expressions must read current runtime storage.

Analysis may retain conservative capacity or NUL facts as internal implementation details for existing planners. Those facts are not a universal INPUT contract and must not force heavyweight learner-facing storage or generated runtime machinery solely to cover every possible host-input edge.

Invalid optimization:

```csharp
int Age = 0;
Age = int.Parse(Console.ReadLine()!);
Console.WriteLine(0); // Wrong: ignores current runtime storage.
```

The later read must use `Age`.

## 14. Runtime Arithmetic And Reachability

Expressions depending on INPUT are evaluated at runtime. Binding and type checking still inspect the complete expression and every source branch.

Left-to-right short-circuiting and selected-path behavior remain unchanged: an unreachable right operand, unselected branch, or zero-iteration loop body does not consume input or produce its runtime failure.

Core Integer semantics are defined by the current core-expression specification. This INPUT specification does not require every target to implement those semantics through identical parsing helpers or error dispatch.

## 15. Evaluator Contract

The reference evaluator receives input through an injectable source so tests do not read the process console directly.

It supports:

- programs that execute no INPUT;
- scripted ordinary input;
- ordered input consumption;
- current-value mutation;
- contained read/conversion failure;
- captured stdout and a concise error result;
- host cancellation where applicable.

The evaluator is the semantic reference for ordinary SMILE behavior. It is not a mandate to copy its internal parser or byte handling into generated learner code.

## 16. CLI And Desktop Execution

Normal CLI execution must let an INPUT program interact with the invoking terminal.

The Desktop must provide a visible interactive console path so the learner can see PRINT output, enter requested lines, and observe completion. Input, execution, process output, cancellation, and toolchain work must remain off the WPF UI thread.

Automated tests may provide scripted standard input to focused active-target runs.

## 17. PRINT Prompts Remain Separate

INPUT has no built-in prompt form.

```smile
PRINT Enter your age:
INPUT Age
```

Current PRINT semantics still append a newline. Do not invent a hidden rule that suppresses PRINT's newline merely because INPUT follows it. A future no-newline output feature requires its own explicit specification.

## 18. Comments And Source Layout

INPUT participates in the ordered source-item model. Comments and blank lines around it remain non-semantic and appear in their normal target-native positions.

```smile
LET Age = 0

REM Ask for the age.
INPUT Age

PRINT {Age}
```

Comment text that happens to contain `INPUT Age` does not execute INPUT.

## 19. Compile Diagnostics

The current compile diagnostics remain:

| Code | Meaning |
|---|---|
| `SMILE1501` | `INPUT` must be followed by whitespace |
| `SMILE1502` | `INPUT` requires a target variable |
| `SMILE1503` | INPUT target must be one identifier |
| `SMILE1504` | Unexpected content follows the INPUT target |
| `SMILE1505` | INPUT target variable is undefined |

These diagnose source syntax and binding, not runtime input data.

## 20. Required Conformance Coverage

Fast compiler and MissionGuardrail tests must cover:

- case-insensitive `INPUT variable` syntax;
- rejection of `INPUT {Name}` and other non-identifier forms;
- declaration-before-use and fixed typing;
- top-level, IF, and WHILE placement;
- current-storage reads after INPUT;
- runtime-unknown statement/branch/loop analysis;
- source-order input consumption;
- active-target generated source using normal C#, C, and MASM constructs;
- the absence of obsolete generated byte readers, 4096-byte contracts, UTF-8 state machines, and generic input dispatch for simple programs.

Focused runtime tests should use ordinary valid input and compare the intended conceptual result. Obscure native edge cases are target-specific tests only when the current target contract intentionally supports them.

Paused target tests remain historical until that target is deliberately re-enabled and brought up to the current specification and Core Principles.

## 21. Normative Ordinary Program

```smile
LET age = 0
PRINT How old are you?
INPUT age
PRINT $"You are {age} years old."
```

For ordinary input such as:

```text
49
```

the program prints the prompt using normal PRINT newline semantics, stores Integer `49`, and then prints:

```text
You are 49 years old.
```

The fixture is normative for SMILE syntax, fixed typing, runtime mutation, interpolation, and beginner-level target complexity. It is not authority for a hidden same-line prompt rule.

## 22. Future Compatibility

Future language work must preserve unless explicitly superseded:

- `INPUT variable` operates on one existing variable;
- curly braces are not accepted around the target;
- the target type remains fixed;
- INPUT is a statement, not an expression;
- successful INPUT changes current runtime storage;
- the post-INPUT value remains runtime-unknown to static propagation;
- only reached INPUT statements consume input;
- no automatic retry or prompt is hidden inside INPUT;
- generated code remains native, idiomatic, and beginner-readable.
