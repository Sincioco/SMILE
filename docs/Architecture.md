# Architecture

SMILE v0.5.1.1 uses the same small direct compiler pipeline as v0.5.0. Generated Warning Hygiene adds no syntax:

```text
Source -> Lexer -> Tokens -> Parser -> Syntax Tree -> Binder -> Bound Program
                                                               -> Sequential Execution Trace
                                                               -> Mutation-Aware Pure Simplifier
                                                               -> Variable Mutation Analysis
                                                               -> Target Integer Profile
                                                               -> Target Generator -> Generated Files
                                                                                      |
                                                                               Optional Toolchain
                                                                                      |
                                                                               Build and Run Result
```

The lexer turns source text into tokens for identifiers, literals, keywords, operators, parentheses, line endings, and end-of-file. It also recognizes a quote followed only by horizontal whitespace and a physical newline as the start of a possible SET Block String Literal, consumes through a structural closing-delimiter line, preserves exact source spans and trailing whitespace, normalizes content boundaries to logical `\n`, removes only the closing delimiter's exact indentation margin from matching lines, and decodes the official shared String escapes. That gives SMILE one official front-end place for block normalization before any target generator is involved.

The parser is normally line-oriented. It recognizes `LET`, `SET`, deterministic `PRINT` forms, raw templates, `$"..."` interpolation, ordinary quoted strings, and typed expressions with precedence. A SET Block String Literal is the single explicit exception: its token makes one logical SET statement span multiple physical lines, while the newline after the closing delimiter terminates the statement normally. The parser enforces that the block is the complete SET value and rejects it in LET, PRINT, interpolation, concatenation, and parentheses.

The binder resolves variable names with an ordinal case-insensitive symbol table and assigns each expression a SMILE type: `String`, `Integer`, or `Boolean`. A `LET` variable is deliberately absent while its initializer binds, then becomes visible only after the initializer succeeds. `SET` resolves an earlier declaration, binds its right side with the old value visible, requires exact type equality, and produces one canonical `BoundSetStatement`. A normalized block binds as an ordinary bound String literal. This keeps declarations-before-use, self-reference, failed declarations, duplicate declarations, undefined SET targets, assignment type mismatches, overflow, and division-by-zero target-independent. Target generators consume the bound program and do not reparse SMILE source text.

The syntax and bound trees each use one canonical representation for every feature. `LetStatementSyntax`, `SetStatementSyntax`, and `PrintStatementSyntax` bind to their corresponding statement nodes. `BlockStringLiteralExpressionSyntax` exists only to preserve placement and source-form information, then binds to an ordinary `BoundStringLiteralExpression`. String concatenation is a typed binary `+`, not a parallel compatibility node, and a SET Block String does not survive as a target-specific bound form. Every target consumes the same bound expressions and can render arithmetic, boolean logic, interpolation, comparison, concatenation, and assignment naturally.

`BoundLetStatement` carries only its variable and initializer; it no longer owns a permanent current `SmileValue`. The reference evaluator executes statements sequentially with a mutable `VariableSymbol -> SmileValue` environment. LET evaluates an initializer and stores the initial value, SET evaluates its complete right side against the old environment and then atomically replaces the current value, and PRINT reads the latest state. `AND` and `OR` remain explicitly left-to-right and short-circuiting, while binding still visits both operands so unreachable undefined names and type errors remain diagnostics.

After binding, `BoundProgramExecutionTrace` symbolically evaluates the program in source order. Its steps contain each `BoundStatementExecution` with the environment before, statement value, and environment after; it also exposes assigned-value history, mutated variables, and final values. The target-independent simplifier consumes that state, folds Boolean identities, and preserves readable expression intent. For SET it simplifies and evaluates the right side using the old environment, then updates the known value only after the whole right side succeeds. No old value is propagated past an assignment.

For `AND` and `OR`, the simplifier first simplifies and evaluates the left operand using the state at that statement. If its known value makes the right side unreachable, the complete expression is replaced immediately and the right subtree is not simplified or evaluated. Binding has already validated that subtree, so undefined names and type errors remain diagnostics while unreachable division or overflow cannot leak into a strict destination compiler. SMILE v0.5.1.1 still has no input, branch, loop, function, or external runtime data, so values remain determinable in order even though variables are mutable.

SMILE `Integer` remains a signed 64-bit semantic type in the binder, evaluator, and language specification. Storage spelling is a target-generation decision. One profile scans the complete statement-order trace, including LET and SET values, literals, operands, reachable intermediates, PRINT expressions, and interpolation holes at the correct statement positions. C and Objective-C use `int` while everything fits signed 32-bit and otherwise use `int64_t` with `INT64_C(...)` or `INT64_MIN`. C++ similarly uses ordinary `int` or `std::int64_t`; C# and Java choose `int` or `long`; JavaScript chooses `Number` while every value is a safe Integer and otherwise uses `BigInt` consistently; Swift chooses `Int` or `Int64`; Python keeps its normal arbitrary-precision `int`.

The engine exposes a small target-local string flattener for targets that need ordered output segments. It derives those segments from the canonical bound tree; it is not a second expression model. It turns bound string expressions such as:

```text
"Hello " + Name + "!"
Hello {Name}!
$"Hello {Name}!"
```

into ordered printable segments:

```text
literal "Hello "
variable Name
literal "!"
```

SMILE Strings are complete length-aware values even when a destination's ordinary representation is not. C and Objective-C keep mutable `const char *` pointers; each String SET right side lowers from the statement-local trace to one exact ordinary C literal and emits pointer assignment. If a variable ever holds NUL, a deterministic collision-safe `size_t smileString{variableIndex}Length` support variable is initialized at LET and updated immediately after every SET pointer update.

The reference evaluator's current state and generated target runtime storage must agree at every observable direct read, not only in the program's final output. C and Objective-C direct String variable PRINT reads the current pointer and, when present, its current logical length; it does not emit an independent statement-local byte copy. Direct String equality uses current target storage where the operands can be represented clearly, with ordinary `strcmp` for NUL-free values and length plus `memcmp` for exact byte-aware values. Highly complex expressions may still use their statement-local known result.

COBOL sizes each `PIC X` from the maximum UTF-8 byte length across LET and every SET value. A mutated variable and every String used by direct PRINT gets a COMP-5 `SMILE-SET-LENGTH-{variableIndex}` field; the generator compares that name with mapped user names case-insensitively and adds a deterministic numeric suffix on collision. Every SET moves both the exact literal and its byte length. Direct variable PRINT reads the current data item and uses the current logical length, with an exact newline-only runtime path when that length is zero. MASM retains `variable{n}Ptr` plus `variable{n}Length`, emits deterministic `variable{n}Value` and `set{statementIndex}Value` byte labels, updates both runtime fields in source order, and reads both fields for direct variable PRINT.

Python emits one dependency-free `Program.py` with a conventional `main()` function and guard. It maps SMILE strings, integers, and booleans to Python `str`, `int`, and `bool`; preserves interpolation as f-strings; and uses native case-sensitive string equality plus short-circuit `and`/`or`. `_smile_text` is emitted only when an Integer or Boolean becomes text so Boolean output remains canonical `TRUE`/`FALSE`. `_smile_div` is emitted only for Integer division and computes with absolute-value floor division before restoring the sign, preserving SMILE truncation toward zero for negative operands.

C++ has its own bound-tree generator rather than reusing C output with another file extension. SMILE Strings become RAII-owned `std::string` values, SET uses natural assignment, interpolation uses `std::to_string` and canonical Boolean text, equality uses native value operators, and `PRINT` uses `std::cout` with `'\n'`. A literal containing embedded NUL uses a UTF-8 byte-counted `std::string{literal, length}` construction, so assignment, streaming, and equality remain exact without target-specific block handling. Header analysis follows the generated C++ facilities, and the dedicated MSVC toolchain compiles `Program.cpp` as C++20 in the same isolated, cancellable temporary-workspace pipeline as C and MASM.

One shared mutation analysis records every variable targeted by SET. Most destinations already use mutable local storage naturally. Swift uses the set to emit `var` only for assigned variables and keeps `let` for declarations that never change.

A direct SMILE self-assignment is semantically a valid no-op, but its SET must remain visible as an actual destination assignment. Destination rules are a separate concern: C# warns about `target = target`, and Swift rejects it. Those two generators recognize only a direct `BoundVariableExpression` whose `VariableSymbol` is the SET target, then emit the smallest type-preserving identity assignment: append an empty String, add Integer zero, or OR Boolean false. Case-insensitive references and mapped identifiers work through symbol identity and the existing target identifier map; assignments from a different symbol remain natural target assignments.

The engine includes a small `SmileEvaluator` reference evaluator. It executes the bound program directly, stores current typed `SmileValue` instances in a mutable symbol environment, applies SET atomically, and appends the current display text for PRINT. Tests use it as the semantic oracle for runnable generated targets. SET, block normalization, exact control-character output, mutation-aware short circuits, direct runtime-storage reads, and small/boundary/wide Integer profiles run through every installed target toolchain and compare output byte-for-byte except for explicitly permitted CRLF/LF normalization. Structural tests additionally verify that C, Objective-C, COBOL, and MASM direct reads reference current target storage rather than an unrelated literal.

The v0.4.2.1 exact-byte suite adds NUL literals, copies, concatenation, interpolation, equality, prefix collisions, and known-variable short circuits in every expression position. It captures stdout without trimming and compares UTF-8 bytes after normalizing only platform CRLF where the test explicitly permits that normalization. NUL, backspace, form feed, carriage return, and tab are never discarded.

Target generators use a symbol-based target identifier map. Valid SMILE identifiers are preserved when safe, and mapped to readable names such as `_smile_class` or `SMILE-class` when they conflict with destination-language keywords, contextual/restricted identifiers, generator-owned runtime names, preprocessor macros, or target-specific reserved identifier patterns. When C, Objective-C, or C++ activates a fixed-width Integer header, names such as `INT64_MAX`, `INT64_C`, `UINT64_MAX`, and `SIZE_MAX` could be macro-expanded before compilation; all three targets therefore share the complete protected fixed-width and limit-macro family. C and Objective-C retain their implementation-reserved prefix checks for `__internal` and `_Upper` and protect every emitted library/type name, including `bool`, `int64_t`, `size_t`, `fwrite`, `fputc`, `strcmp`, `memcmp`, and `strlen`. C++ additionally treats a double underscore anywhere as reserved, then spells those underscore runs out in the `_smile_` result so the final emitted name is safe rather than merely prefixed. C++ also protects all C++20 keywords and generator-used `std` names. COBOL maps underscores and reserved words to hyphenated COBOL data names. Java and Swift map a single `_` because it is not a usable ordinary local variable in those targets. Python protects its keywords, `match`/`case` soft keywords, relevant built-ins, `main`, `__name__`, `_smile_text`, and `_smile_div`; a single `_` remains valid. The map is built once per target from `BoundProgram.Variables`, so every reference to a variable uses the same generated name as its declaration.

MASM direct variable PRINT reads `variable{n}Ptr` and `variable{n}Length`, so it observes every prior SET. Complex PRINT retains exact statement-local static bytes. For an empty String, a data label may keep a one-byte placeholder so the symbol has an address while the logical length remains `0`.

Generated target code should be semantically correct, idiomatic for the destination language, and close to code a competent human developer would naturally write. That rule applies even when a lower-level target must lower SMILE features into equivalent operations.

`SMILE.Engine` has no WPF dependency. That keeps the language front end reusable from the CLI, the desktop app, tests, and a possible future web interface.

`SMILE.Toolchains` owns local compiler/runtime detection, process execution, target availability status, separate build/program timeouts, bounded process output, and optional press-any-key launcher scripts. Java detection requires both `javac` and `java` for a full-JDK status and distinguishes that state from a runtime-only installation or a missing JDK. C++ uses the Visual Studio x64 environment and MSVC C++20, COBOL uses MSYS2 GnuCOBOL, Objective-C uses MSYS2 Clang for SMILE's Foundation-free console profile, Swift uses Swift.Toolchain with the Visual Studio C++ linker environment, and Python discovers an existing Python 3.10+ interpreter while skipping Windows Store aliases that could trigger installation. Process work is asynchronous, cancellable, timed, and isolated in `%TEMP%\SMILE\Runs\<unique-id> - <language>\` so the WPF UI thread stays responsive, learners can identify each generated-code folder, and build artifacts stay out of the repository.

Release validation treats the SMILE solution build and generated target builds as separate warning surfaces. A zero-warning solution build cannot hide a warning in generated code. With `SMILE_REQUIRE_ZERO_TARGET_WARNINGS=1`, tests compile generated C# through the existing asynchronous toolchain infrastructure, inspect retained compiler output for C# warning diagnostics, and fail independently of solution-build warning totals. This validation stays in tests and explicit Build & Run paths; live transpilation never invokes a destination compiler on the WPF dispatcher.

The desktop app tracks source revisions for live preview. Its view model starts with an empty editor and performs no language-reference file I/O or compiler work during window construction. A one-shot `ContentRendered` handler waits until WPF has completed the first paint, yields once behind pending render/input work, then asynchronously reads the deployed `language.smile` file and generates only the three visible targets through the background compiler path. The startup read applies its text only if the source revision and file association are still untouched, so typing or opening a document during that read cannot be overwritten. Typing schedules the same short debounced background transpilation for visible target languages only. Manual Transpile All runs asynchronously and generates all ten targets. Build & Run asks for the current source revision before invoking a toolchain, which prevents a compiler from running stale generated code.

`SMILE.Desktop` uses AvalonEdit for the editable SMILE source pane and the three generated target panes. Those four code panes show line numbers and lexical syntax highlighting, while the output area stays a plain append-only log for build and program output. The SMILE definition highlights `SET` as a keyword and keeps a quote-at-line-end block span active until a whitespace-only closing delimiter line, so quotes inside content do not end highlighting. This remains a small lexical rule rather than running the compiler on the UI thread. Target definitions are loaded lazily so rapid typing and language switching stay responsive.

Generated programs are cached by target language and source revision. A target-language switch first tries that cache; live transpilation is scheduled only for visible targets that are missing for the current source revision. This keeps rapid ComboBox changes responsive and avoids unnecessary compiler work on the WPF dispatcher path.

C++ is the tenth and final planned destination language. Target-language expansion remains frozen unless Sin explicitly reopens it, so architecture work after the syntax-free v0.5.1.1 warning-hygiene release can proceed to v0.6.0 `IF / THEN / ELSE`, then deepen input, loops, functions, scopes, debugging, and teaching tools. Rust, Zig, and Go remain deferred rather than active targets.

Recoverable desktop failures are contained at the operation boundary. Language-reference loading, toolchain detection, build/run, child-process output, command-state refresh, and folder-opening failures report concise output, write a diagnostic log when possible, and keep the IDE open.

KISS keeps the architecture small: one engine project, one toolchain project, one CLI harness, one desktop app, and one test project. KISS v2 keeps the user experience responsive first.
