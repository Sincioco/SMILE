# Architecture

SMILE v0.6.0 keeps the small direct compiler pipeline and adds recursive block conditionals plus branch-aware analysis:

```text
Source -> Lexer -> Tokens -> Recursive Block Parser -> Syntax Tree -> Binder -> Bound Program
                                                                         -> Branch-Aware Statement Analysis
                                                                         -> Mutation-Aware Pure Simplifier
                                                                         -> Variable Mutation Analysis
                                                                         -> Target Integer/String Planning
                                                               -> Target Generator -> Generated Files
                                                                                      |
                                                                               Optional Toolchain
                                                                                      |
                                                                               Build and Run Result
```

The lexer turns source text into tokens for identifiers, literals, case-insensitive keywords including `IF`, `THEN`, `ELSE`, and `END`, operators, parentheses, line endings, and end-of-file. It does not create combined ELSEIF or ENDIF tokens. It also recognizes a quote followed only by horizontal whitespace and a physical newline as the start of a possible SET Block String Literal, consumes through a structural closing-delimiter line, preserves exact source spans and trailing whitespace, normalizes content boundaries to logical `\n`, removes only the closing delimiter's exact indentation margin from matching lines, and decodes the official shared String escapes. That gives SMILE one official front-end place for block normalization before block parsing or target generation.

The parser retains the source-line model but parses recursive statement lists. A top-level list recognizes `LET`, `SET`, deterministic `PRINT` forms, and block `IF`; an IF body recursively consumes statements until the nearest matching ELSE IF, ELSE, or END IF. ELSE and IF form an ELSE IF clause only on the same logical header line. An IF following a standalone ELSE line is a nested statement and consumes its own END IF. Token-aware header parsing finds the actual THEN token rather than treating THEN text inside a String or interpolation as a terminator. A SET Block String token remains one logical SET statement across its physical content lines, so block contents cannot be mistaken for IF terminators.

The binder resolves variable names with an ordinal case-insensitive symbol table and assigns each expression a SMILE type: `String`, `Integer`, or `Boolean`. A `LET` variable is deliberately absent while its initializer binds, then becomes visible only after the initializer succeeds. `SET` resolves an earlier declaration, binds its right side with the old value visible, requires exact type equality, and produces one canonical `BoundSetStatement`. For each IF clause, the binder binds the unsimplified condition, validates that every Boolean leaf is an explicit comparison, rejects future call or invocation nodes by default, requires a Boolean result, and binds every body even when an earlier condition is known true. IF v1.0 rejects LET in every branch because v0.6.0 introduces no block scope. A normalized block binds as an ordinary bound String literal. This keeps block shape, declarations-before-use, type rules, overflow, and division-by-zero target-independent.

The syntax and bound trees each use one canonical representation for every feature. `IfStatementSyntax` contains ordered conditional clauses and an optional final ELSE body; `BoundIfStatement` contains the corresponding bound clauses and bodies. The first clause is IF and later clauses are ELSE IF. `LetStatementSyntax`, `SetStatementSyntax`, and `PrintStatementSyntax` continue to bind to their corresponding statement nodes. `BlockStringLiteralExpressionSyntax` exists only to preserve placement and source-form information, then binds to an ordinary `BoundStringLiteralExpression`. Every target consumes the same recursive bound tree and never inspects IF or block-String source text.

`BoundLetStatement` carries only its variable and initializer; it does not own a permanent current `SmileValue`. The reference evaluator executes recursive statement lists with a mutable `VariableSymbol -> SmileValue` environment. LET evaluates an initializer and stores the initial value, SET evaluates its complete right side against the old environment and then atomically replaces the current value, PRINT reads the latest state, and IF tests clauses in order using current runtime values. Only the first successful clause or final ELSE body executes and mutates the environment. Nested IF uses the same evaluator path. `AND` and `OR` remain explicitly left-to-right and short-circuiting, while binding still visits both operands and every branch.

After binding, `BoundProgramAnalysis` walks recursive statement lists in source order with `Known(SmileValue)` or `Unknown` facts. Each IF branch starts from the same incoming environment. Outgoing paths merge to Known only when every possible path proves the same value; different values, known/unknown mixtures, and a changed branch merged with an unchanged path become Unknown unless their values agree. An IF without ELSE includes the implicit unchanged path. The shared recursive analysis also records assigned values, mutated variables, bounded per-expression display length and NUL possibility, Integer ranges, and statement/clause facts used by storage planning, simplification, and target generation across the complete IF tree. A companion concrete trace remains the reference evaluator's one selected execution, but it cannot authorize a static target value where branch-aware analysis reports Unknown.

The target-independent simplifier consumes the analysis state, folds safe Boolean identities, and preserves readable expression intent. For SET it uses the old environment and changes the known value only after the complete right side succeeds. For `AND` and `OR`, it simplifies the left operand first and never simplifies or evaluates an unreachable right subtree. Explicit-comparison validation occurs before simplification so `= TRUE` cannot disappear before validation. A known condition may guide facts inside a branch, but simplification never replaces an entire IF, deletes a clause or ELSE body, or carries one branch's value into another.

SMILE `Integer` remains a signed 64-bit semantic type in the binder, evaluator, and language specification. Storage spelling is a target-generation decision. One profile scans every LET and SET value, IF and ELSE IF condition, literal, operand, intermediate, PRINT expression, interpolation hole, and nested branch, including branches not selected by current values. C and Objective-C use `int` while everything fits signed 32-bit and otherwise use `int64_t`; C++ similarly uses ordinary `int` or `std::int64_t`; C# and Java choose `int` or `long`; JavaScript chooses `Number` or a whole-program `BigInt` profile; Swift chooses `Int` or `Int64`; Python keeps its arbitrary-precision `int`.

The engine exposes a small target-local string flattener for targets that need ordered output segments. It derives those segments from the canonical bound tree; it is not a second expression model. It turns bound string expressions such as:

```text
"Hello " + Name + "!"
Hello {Name}!
$"Hello {Name}!"
```

into ordered printable segments:

```text
literal "Hello "
variable Name
literal "!"
```

SMILE Strings are complete length-aware values even when a destination's ordinary representation is not. C and Objective-C keep mutable `const char *` pointers. Branch-aware Known String assignments may lower to exact ordinary C literals; runtime-unknown direct SET and later LET operations copy current source storage, while Unknown composite assignments materialize current runtime segments into bounded deterministic buffers. Pointer and logical-length metadata stay synchronized after every update. If a variable can hold NUL on any path, a deterministic collision-safe `size_t smileString{variableIndex}Length` support variable accompanies it.

The reference evaluator's current state and generated target runtime storage must agree at every observable expression, not only in the program's final output. String planning considers every value assigned on every branch, the maximum UTF-8 byte length, embedded-NUL possibility, logical-length requirements, and post-IF reads. C and Objective-C direct String variable PRINT reads the current pointer and, when present, its current logical length. Composite assignment, output, interpolation, and equality materialize or stream current runtime segments when their value is Unknown, with ordinary `strcmp` for safely NUL-free values and length-aware byte operations for exact values.

COBOL sizes each `PIC X` from the maximum UTF-8 display-byte length across LET and every SET value in every branch. A mutated variable and every String used by direct PRINT gets a collision-safe logical-length field. Branch-aware Known assignments move an exact value and length; runtime-unknown direct assignments copy current source storage, and Unknown composite LET, SET, output, and condition expressions use runtime `STRING`, numeric display, and condition plans. Generated IF / ELSE / END-IF preserves clause order and storage reads. MASM retains pointer-plus-length storage plus signed runtime Integer fields, emits deterministic branch and value labels, uses genuine compare/jump control flow, copies direct values without mutable-buffer aliasing, materializes Unknown composite expressions in bounded statement-local storage, formats signed Integers at runtime, updates fields only in selected branches, and reads current fields for direct or composite runtime output and conditions.

Python emits one dependency-free `Program.py` with a conventional `main()` function and guard. It maps SMILE strings, integers, and booleans to Python `str`, `int`, and `bool`; preserves interpolation as f-strings; and uses native case-sensitive string equality plus short-circuit `and`/`or`. `_smile_text` is emitted only when an Integer or Boolean becomes text so Boolean output remains canonical `TRUE`/`FALSE`. `_smile_div` is emitted only for Integer division and computes with absolute-value floor division before restoring the sign, preserving SMILE truncation toward zero for negative operands.

C++ has its own bound-tree generator rather than reusing C output with another file extension. SMILE Strings become RAII-owned `std::string` values, SET uses natural assignment, interpolation uses `std::to_string` and canonical Boolean text, equality uses native value operators, and `PRINT` uses `std::cout` with `'\n'`. A literal containing embedded NUL uses a UTF-8 byte-counted `std::string{literal, length}` construction, so assignment, streaming, and equality remain exact without target-specific block handling. Header analysis follows the generated C++ facilities, and the dedicated MSVC toolchain compiles `Program.cpp` as C++20 in the same isolated, cancellable temporary-workspace pipeline as C and MASM.

One shared recursive mutation analysis records every variable targeted by SET anywhere in the IF tree. Most destinations use mutable local storage naturally. Swift uses the complete set to emit `var` even when assignment appears only in a currently unselected branch and keeps `let` only for declarations never assigned on any path.

A direct SMILE self-assignment is semantically a valid no-op, but its SET must remain visible as an actual destination assignment. Destination rules are a separate concern: C# warns about `target = target`, and Swift rejects it. Those two generators recognize only a direct `BoundVariableExpression` whose `VariableSymbol` is the SET target, then emit the smallest type-preserving identity assignment: append an empty String, add Integer zero, or OR Boolean false. Case-insensitive references and mapped identifiers work through symbol identity and the existing target identifier map; assignments from a different symbol remain natural target assignments.

The engine includes a small `SmileEvaluator` reference evaluator. It executes the recursive bound program directly, stores current typed `SmileValue` instances in a mutable symbol environment, applies SET atomically, selects exactly one IF branch, and appends current display text for PRINT. Tests use it as the semantic oracle for runnable generated targets. The official IF program and cumulative `language.smile` reference run through every installed target toolchain. The evaluator-side clause-selection matrix separately exercises every possible selected clause and the no-ELSE path. Structural generation tests cover nested branches, branch Block Strings, exact control-byte and Integer-profile planning, preservation of every source branch, and lower-level reads from current target storage.

The v0.4.2.1 exact-byte suite adds NUL literals, copies, concatenation, interpolation, equality, prefix collisions, and known-variable short circuits in every expression position. It captures stdout without trimming and compares UTF-8 bytes after normalizing only platform CRLF where the test explicitly permits that normalization. NUL, backspace, form feed, carriage return, and tab are never discarded.

Target generators use a symbol-based target identifier map. Valid SMILE identifiers are preserved when safe, and mapped to readable names such as `_smile_class` or `SMILE-class` when they conflict with destination-language keywords, contextual/restricted identifiers, generator-owned runtime names, preprocessor macros, or target-specific reserved identifier patterns. When C, Objective-C, or C++ activates a fixed-width Integer header, names such as `INT64_MAX`, `INT64_C`, `UINT64_MAX`, and `SIZE_MAX` could be macro-expanded before compilation; all three targets therefore share the complete protected fixed-width and limit-macro family. C and Objective-C retain their implementation-reserved prefix checks for `__internal` and `_Upper` and protect every emitted library/type name, including `bool`, `int64_t`, `size_t`, `fwrite`, `fputc`, `fputs`, `strcmp`, `memcmp`, `memcpy`, `strlen`, and `snprintf`. C++ additionally treats a double underscore anywhere as reserved, then spells those underscore runs out in the `_smile_` result so the final emitted name is safe rather than merely prefixed. C++ also protects all C++20 keywords and generator-used `std` names. COBOL maps underscores and reserved words to hyphenated COBOL data names. Java and Swift map a single `_` because it is not a usable ordinary local variable in those targets. Python protects its keywords, `match`/`case` soft keywords, relevant built-ins, `main`, `__name__`, `_smile_text`, and `_smile_div`; a single `_` remains valid. The map is built once per target from `BoundProgram.Variables`, so every reference to a variable uses the same generated name as its declaration.

MASM direct variable PRINT reads `variable{n}Ptr` and `variable{n}Length`, so it observes every prior SET. Complex PRINT retains exact static bytes only when branch-aware analysis proves the complete value; otherwise it lowers runtime storage and expressions. For an empty String, a data label may keep a one-byte placeholder so the symbol has an address while the logical length remains `0`.

Generated target code should be semantically correct, idiomatic for the destination language, and close to code a competent human developer would naturally write. That rule applies even when a lower-level target must lower SMILE features into equivalent operations.

`SMILE.Engine` has no WPF dependency. That keeps the language front end reusable from the CLI, the desktop app, tests, and a possible future web interface.

`SMILE.Toolchains` owns local compiler/runtime detection, process execution, target availability status, separate build/program timeouts, bounded process output, and optional press-any-key launcher scripts. Java detection requires both `javac` and `java` for a full-JDK status and distinguishes that state from a runtime-only installation or a missing JDK. C++ uses the Visual Studio x64 environment and MSVC C++20, COBOL uses MSYS2 GnuCOBOL, Objective-C uses MSYS2 Clang for SMILE's Foundation-free console profile, Swift uses Swift.Toolchain with the Visual Studio C++ linker environment, and Python discovers an existing Python 3.10+ interpreter while skipping Windows Store aliases that could trigger installation. Process work is asynchronous, cancellable, timed, and isolated in `%TEMP%\SMILE\Runs\<unique-id> - <language>\` so the WPF UI thread stays responsive, learners can identify each generated-code folder, and build artifacts stay out of the repository.

Release validation treats the SMILE solution build and generated target builds as separate warning surfaces. A zero-warning solution build cannot hide a warning in generated code. With `SMILE_REQUIRE_ZERO_TARGET_WARNINGS=1`, tests inspect destination-specific compiler output for the compiler-backed targets while identifying JavaScript and Python as interpreter-only. Official IF and cumulative-reference runs also require exit code zero and exact `SmileEvaluator` output. This validation stays in tests and explicit Build & Run paths; live transpilation never invokes a destination compiler on the WPF dispatcher.

The desktop app tracks source revisions for live preview. Its view model starts with an empty editor and performs no language-reference file I/O or compiler work during window construction. A one-shot `ContentRendered` handler waits until WPF has completed the first paint, yields once behind pending render/input work, then asynchronously reads the deployed `language.smile` file and generates only the three visible targets through the background compiler path. The startup read applies its text only if the source revision and file association are still untouched, so typing or opening a document during that read cannot be overwritten. Typing schedules the same short debounced background transpilation for visible target languages only. Manual Transpile All runs asynchronously and generates all ten targets. Build & Run asks for the current source revision before invoking a toolchain, which prevents a compiler from running stale generated code.

`SMILE.Desktop` uses AvalonEdit for the editable SMILE source pane and the three generated target panes. Those four code panes show line numbers and lexical syntax highlighting, while the output area stays a plain append-only log. The SMILE definition highlights IF, THEN, ELSE, and END individually, and keeps a quote-at-line-end block span active until a whitespace-only closing delimiter line even inside a branch. This remains a small lexical rule rather than running the compiler on the UI thread. Target definitions are loaded lazily so nested IF typing and rapid language switching stay responsive.

Generated programs are cached by target language and source revision. A target-language switch first tries that cache; live transpilation is scheduled only for visible targets that are missing for the current source revision. This keeps rapid ComboBox changes responsive and avoids unnecessary compiler work on the WPF dispatcher path.

C++ is the tenth and final planned destination language. Target-language expansion remains frozen unless Sin explicitly reopens it. After v0.6.0 IF / ELSE IF / ELSE, architecture work deepens input, loops, functions, scopes, debugging, and teaching tools. Rust, Zig, and Go remain deferred rather than active targets.

Recoverable desktop failures are contained at the operation boundary. Language-reference loading, toolchain detection, build/run, child-process output, command-state refresh, and folder-opening failures report concise output, write a diagnostic log when possible, and keep the IDE open.

KISS keeps the architecture small: one engine project, one toolchain project, one CLI harness, one desktop app, and one test project. KISS v2 keeps the user experience responsive first.
